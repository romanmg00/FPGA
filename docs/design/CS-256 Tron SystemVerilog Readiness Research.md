# CS-256 Tron SystemVerilog Readiness Research

Research date: **2026-10-28**. This is a draft investigation for the parent interview, not an accepted architecture or Roman's agreement. No HDL, implementation changes, ADR adoption, commits, pushes or external messages were made. The companion readiness Decisions note belongs to the parent and was not edited.

The model is a useful rules reference and a candidate shared-model base. It is **not yet a cycle-accurate blueprint** for independent blocks. Freeze register ownership and functional outcome types first; freeze X1, input and render ports only after their timing, ordering and visibility policies are explicit. The principal blockers are the slow-side transaction budget, coherent Arena/sprite publication, input eligibility across delayed delivery, and bounded concurrent Reward search. These conclusions follow from the implementation and authority evidence below; recommendations remain proposals.

## 3. Clock relationship, X1 and the six-tick budget

### What is actually known

ADR 0002 retains **game-state registers on a real divided ~60 Hz clock**, from a second Wizard; it explicitly leaves the fast service, crossings and coherent scheduling open. It does not authorize moving the game engine to `clk_pix` behind a frame enable. [ADR 0002 — Consequences](../adr/0002-follow-ta-divided-game-clock.md#consequences); [course handout — Drawing Logic Module, steps 10–12](../../../cs256-fall-2026/classproject/README.md#drawing-logic-module).

The isolated UART experiment generated **83.45588235294117 MHz**, a **5 MHz** second output, and a toggle every **41667** base cycles: **59.99952000384 Hz**. These are configured/generated calculations against a nominal board oscillator, not frequency measurements. The retained `clocks.rpt` defines the game clock at BUFG/O with divide-by **83334** and source `game_toggle_reg/C`; `run.tcl:126–138` deliberately leaves divider feedback timed at 5 MHz. [Clock arithmetic](../../prototipos/fpga/I2-uart-input-prototype/clock-arithmetic.txt), [clocks report](../../prototipos/fpga/I2-uart-input-prototype/clocks.rpt), [experiment findings — CDC review](CS-256%20UART%20Input%20Prototype%20Findings.md#cdc-review-and-constraints).

A common 100 MHz source does not by itself establish safely timed communication. AMD treats relationships with no common period found within its 1000-cycle expansion as asynchronous for crossing/constraint purposes. [UG903 **2026.1**, Unexpandable Clocks](https://docs.amd.com/r/en-US/ug903-vivado-using-constraints/Unexpandable-Clocks), accessed 2026-10-28. Define primary/generated clocks before dependent exceptions. [UG903 **2025.2**, Recommended Constraints Sequence](https://docs.amd.com/r/2025.2-English/ug903-vivado-using-constraints/Recommended-Constraints-Sequence), accessed 2026-10-28.

**Arithmetic inference:** the generated frequencies imply pixel/game ratio **2,781,885 / 2**. Ignoring phase offsets, a rate-only common repeat is two game periods and 2,781,885 pixel periods; this already involves millions of fast cycles. It is not proof of an expandable Vivado relationship. The retained `clock-interaction.rpt` labels actual crossing paths ignored under max-delay/false-path exceptions, so its positive slack does not prove that an unprotected mailbox can be conventionally timed. Re-run clock interaction on the actual chosen topology before selecting any timing exception.

### Options and provisional recommendation

| Option | Viability and cost | Required evidence |
|---|---|---|
| Current single-capture return bus | `mailbox.py:1–27,76–94` assumes a fast response settles long before the next game edge, then is used one edge later. A capture register alone does not establish bus coherence. `seq` changing with payload also needs protection. This could only be retained with a complete constrained causal-window proof, stable hold contract, startup/epoch treatment and overrun containment. | Minimum and maximum data/control paths, no payload changes in capture aperture, post-route constraints/CDC review, adversarial near-edge tests. Do not select solely to match Python's two-tick latency. |
| Full-handshake bus macros | Recognizable bundled transfer with configurable synchronizer depth. However, receipt and rearming are distinct events; source reuse waits for the full cycle. | Waveform with actual source/destination synchronizer settings and same-edge consumer rules; measure **next send allowed**, not only first `dest_req`. |
| Toggle request/acknowledgement with held payload | Potentially fits a smaller budget and one-outstanding discipline; request/response correspondence can overlap useful work. Still a custom CDC protocol requiring stable bundled data, constrained delays, reset alignment and safe destination capture. | Formal/protocol assertions, phase sweeps, reset recovery, routed bundled-data paths. Epoch changes cannot themselves be unsynchronized multi-bit buses. |
| Command/response async FIFOs | Decouple reuse from four-phase bus rearm; full/empty and output latency can consume slow edges. More storage/control and explicit fullness/reset behavior. | Exact configured standard/FWFT timing, registered-output consumer edge, occupancy and credit behavior. No inference from the UART FIFO to a different IP configuration. |

AMD's full-handshake macro requires acknowledgement and signal reset before reuse; its valid output must be captured according to internal/external acknowledgement mode. [UG953 **2024.2**, XPM_CDC_HANDSHAKE, Introduction and port descriptions](https://docs.amd.com/r/2024.2-English/ug953-vivado-7series-libraries/XPM_CDC_HANDSHAKE), accessed 2026-10-28. The 2025.2 page could not be fetched; verify installed 2025.2 implementation/templates before selection.

AMD's async FIFO has configuration-dependent full/empty/read latencies and prohibits transfers while reset/busy is asserted. For standard mode with two synchronization stages, its documented empty deassertion includes four read-domain cycles plus a write-domain cycle; read-output latency is additional. [UG953 **2025.2**, XPM_FIFO_ASYNC, Latency and reset ports](https://docs.amd.com/r/2025.2-English/ug953-vivado-7series-libraries/XPM_FIFO_ASYNC), accessed 2026-10-28. This is the 7-series guide, not a Versal template.

**Budget to prove, not a universal minimum:** six game periods are **100.0008 ms** using the retained divider. The current model needs READ2 outcome by `k+2`, COMMIT retirement by `k+4`, and next launch at `k+6`; it asserts overrun if not ready (`game_top.py:145–148`). A protocol taking three slow edges per dependent round trip spends the whole nominal six-edge budget before extra rearm, response consumption or display waits. A FIFO can differ, as can overlapping rearm or an alternative request schedule. Conversely, the retained UART FIFO's first registered read took about **66.649 ms**, and a synchronous consumer needs its next game edge: blindly using that path twice would not reproduce the model's budget. [Experiment findings — Portable HDL observations and routed results](CS-256%20UART%20Input%20Prototype%20Findings.md).

**Recommendation:** prototype X1 with explicit valid/ready/completion and no assumed `STEP_LATENCY=2`. Compare one-outstanding toggle/bundled transfer against configured XPM alternatives; choose the simplest that proves six-tick steady launch spacing for READ2→slow resolve→COMMIT, including rearm, worst service and display scheduling. Do not add a decision that a slower Step is acceptable: six ticks is agreed. Team chooses protocol and interface; measured latency is an engineering fact. If no candidate fits, revise the transaction decomposition within the accepted game/service boundary, then return the evidence to the team.

### Startup, reset and Pause

**Evidence:** Python resets all domains atomically and clears the Arena immediately (`game_top.py:87–119`, `arena_ctrl.py:43–53`). Hardware does neither automatically. The experiment uses a stretched reset and disables Wizard reset/locked ports; its findings explicitly exclude lock-aware recovery. Clocking Wizard exposes reset behavior separately from configured output timing. [PG065 **v6.0**, 2022-04-20, Resets](https://docs.amd.com/r/en-US/pg065-clk-wiz/Resets), accessed 2026-10-28.

**Proposal:** keep all clocks running through Pause. Use domain-local synchronous active-high `rst`, a defined startup-ready barrier, cleared command/event queues, and coordinated epoch invalidation. Either hold both sides reset until stable clocks and clear completion, or add a startup/reset supervisor; validate course compatibility if enabling `locked` requires changing the course's Wizard settings. A four-bit sequence number is not a reset epoch. No old response/write/event may survive into a new game after reset, including sequence wrap/reuse.

For Pause, distinguish three cases: before READ2 launch, after READ2 but before logical outcome, and after COMMIT issue. The model holds outcomes/timers while paused but lets issued COMMIT retire (`game_top.py:159–178`). **Provisional policy:** issued atomic writes finish, with corresponding already-registered logical outcome; no new Step or Reward publication advances paused visible state unless it belongs to that already-issued transaction. Decide whether a pending replacement search may progress internally and hold its visible installation until resume. Never cancel only half a write list. The spec requires frozen logical state, not a stopped clock. Prerequisites: publication point and issue/complete definitions. Acceptance: reset/Pause at every FSM state and either side of every boundary, no duplicate score, partial Step, stale publication or post-reset write. This requires team interpretation of visible timing plus measured protocol behavior; Python's instant execution does not exercise the difficult interval.

## 4. Coherent rendering and BRAM semantics

**Evidence:** `Game._fast_after_edge()` executes all Arena writes then latches render state (`game_top.py:241–263`); `snapshot()` reads reward slots directly (`:282–303`). The PC frame cannot expose a mid-frame write or stale sprite snapshot. The Hardware Map's limitations and the review's adoption limits explicitly leave this unresolved. A vblank snapshot alone cannot make earlier writes to a live Arena coherent.

**Exact device fact:** in common-clock TDP BRAM, A writing READ_FIRST with B reading the same address returns old data on B; with A WRITE_FIRST or NO_CHANGE, B's colliding read is undefined. Independent-clock same-address write/read can also yield undefined read data. Modes describe more than the writer's own output. [UG473 **v1.14**, 2019-07-03, Conflict Avoidance, Tables 1-4/1-5, pp. 19–20](https://docs.amd.com/v/u/en-US/ug473_7Series_Memory_Resources), accessed 2026-10-28. Hence “write first means display sees the new value” is false as a general cross-port claim.

Pin TDP/SDP, common/independent clocks, mode, enables, primitive/core output registers and read latency. PG058's generated Summary reports per-port read latency, which changes with output-register selection. [PG058 **v8.4**, 2021-08-06, Collision Behavior pp. 51–53, Summary p. 88 and Appendix D](https://docs.amd.com/v/u/en-US/pg058-blk-mem-gen), accessed 2026-10-28. Prefer one fast clock for Arena/display ports initially to avoid an unnecessary independent-clock collision problem; this does not change the selected game clock.

| Coherent approach | Genuinely viable conditions | Tradeoff / failure to avoid |
|---|---|---|
| Schedule Arena writes and paired sprite metadata in vertical blank | Hold a complete versioned update until blank; apply every write and metadata before the first prefetched visible pixel. Game READ2 must see the appropriate completed prior Step. PREPARE can use a defined hidden/not-ready display until complete. | May wait nearly a frame. Account for this in X1; a one-period response deadline may be impossible if the request arrives just after blank. Acknowledge enqueue and completion separately only if the next READ is fenced correctly. |
| Forwarding / versioned overlay | Buffer the small delta with old and new cell values; select the version matching the visible snapshot for every affected read. Publish metadata and selection atomically at a frame boundary. | A simple same-cycle address comparator fixes a BRAM hazard, **not frame coherence**. Need enough retained old data and queue space for all updates before publication, handling Rewards and clear. |
| Separate display copy | Game/service storage updates independently. During blank apply versioned deltas to display Arena and latch matching sprites; or prepare an inactive complete copy, then swap at a safe boundary. | Additional 32768 bits per Arena copy plus actual mapping overhead, delta queue/copy bandwidth, reset/clear and copy catch-up. Swapping stale alternating banks without replay/copy is incorrect. |

**Arithmetic feasibility only:** retained raster has 28 non-visible lines × 1680 = **47040** fast cycles, approximately **0.564 ms** at generated pixel rate. A contiguous vertical-blank window spans the frame wrap; place its start/end relative to early reads, not just `vsync`. The model's ideal worst PREPARE count is `8192 + 2 + 3×(64×33 + 8192 + 1) = 39109` cycles, already close enough that latency/arbitration can matter. An ideal full-copy pipeline issuing one word per cycle takes about 8192 cycles plus fill/drain, but real port availability is unproved. No figure establishes timing closure. [Raster constants: contract §5; controller and placement counts: `arena_ctrl.py`, `reward_place.py`; generated clock arithmetic cited above.]

**Recommendation:** first compare scheduled small commits with a separate display copy/delta replay. Keep forwarding as an option only with explicit version retention. Display publication may lag the logical game; the spec does not forbid that, but team agreement is needed on its presentation and Pause implications. Acceptance: cycle-accurate renderer scoreboard proves each full visible frame uses one version of Arena, heads, shown Heading, Reward identity/validity and Crash state, across every relative game/frame phase, including clear/preparation and Pause. Assert no visible or prefetched read consumes an unspecified collision result. Exact RAM modes/latencies are engineering configuration facts; tolerable latency and chosen coherence policy are team decisions.

## 5. Arena controller and replacement service

**Retain:** the one write owner, padded address map, inaccessible-cell initialization, both-target-before-movement writes, slot identity and bounded fallback concept. **Redesign:** `ArenaMap.clear()` is a bytearray copy; reads return immediately; `ArenaCtrl.execute()` loops synchronously through a whole command. Its `cycles` is a bookkeeping estimate and `overrun` merely a Boolean; it neither stalls real callers nor measures a generated design. [Model `arena_map.py:1–8,59–92`, `arena_ctrl.py:1–20,55–112`, `reward_place.py`.]

**Proposed sequential FSMs:**

- Clear: issue one address/write each enabled fast cycle through all 8192 locations, writing `clear_word`, then heads. Return ready only after initialization and all three initial slots succeed as required.
- READ2: capture immutable targets, issue/tag reads, wait for actual A-port latency, capture both codes before movement writes; no response until both are valid.
- COMMIT: validate bounded write count, apply ordered head/Trail writes once, invalidate collected slots and return completion at the chosen linearization point. Track logical, Arena and display version correspondence.
- Placement: generate candidate, issue read, wait/tag, accept only EMPTY playable cells, then write atomically relative to other writers. After 64 rejected random candidates, scan at most all 8192 addresses once, with an explicit terminal count/wrap flag; return ABSENT/full rather than retry forever.

Synchronous reads, controlled writes and a sequential clear preserve the proposed BRAM structure. Do not reset every array word in a reset branch. Generated primitive count and port latency must be verified by synthesis/IP simulation; 32768 payload bits alone do not prove one physical BRAM. [Contract §4 `arena_map`; UG473/PG058 above.]

**Same-COMMIT versus background replacement:** current `_commit()` replaces collected slots in sorted order before responding; that is permitted if bounded sufficiently, but the specification does **not require it**. It explicitly permits temporary absence while play continues. Alternatives: retain bounded in-command search (simpler reproducibility, longer critical service); or prioritize Step READ2/COMMIT and service search in bounded fast-cycle quanta (shorter Step latency, arbitration/revalidation complexity). [Specification — Rewards and randomness; model `arena_ctrl.py:97–112`.]

**Recommendation:** separate movement-write completion from replacement completion unless measurements show a comfortably bounded integrated command. PREPARE still waits for three initial Rewards. Give gameplay commands a bounded maximum wait, and give each absent slot a bounded search quantum/fair slot order so it cannot starve. A fully serialized integrated command needs no stale-candidate recheck between its uninterrupted occupancy read and write. A preemptible background search must re-read/revalidate **under exclusive ownership immediately before writing**; if invalid, resume bounded search. Reserve or serialize simultaneous slot installations to avoid duplicate Rewards. Define whether LFSR draws happen on candidate creation or after revalidation failures and whether waiting advances it.

Full-Arena termination remains sound because Trails/head occupancy never free cells during a Round; collecting a Reward replaces its cell with a head, not EMPTY. That monotonicity permits one complete fallback traversal to prove no empty cell, even if occupancy increases during traversal, provided each location is actually read and the final candidate is revalidated. A 13-bit wrapping address alone cannot distinguish zero reads from 8192 reads; use a completed-pass flag or 14-bit count. [Specification — Movement, Turns and Crashes / Rewards; `reward_place.py:1–25,48–55`.]

**Engineering acceptance:** parameterized memory latency, full map, sole remaining EMPTY, last-address EMPTY, wrap, simultaneous collections, candidate occupied during preemption, reset/round epoch change, bounded foreground wait and bounded search completion. Derive a conservative symbolic service bound from cycles per read/draw/write plus arbitration, then measure it. Require a hardware fault response/diagnostic on an exceeded bound; do not silently slow the six-tick game or publish incomplete results. Team selects service ordering and disappearance presentation; it need not vote on measured BRAM latency.

## 6. PRNG, reproducibility and numeric widths

**Current algorithm:** 32-bit left-shift Fibonacci recurrence `new_bit0 = old[31] ^ old[21] ^ old[1] ^ old[0]`, masked to 32 bits; one draw advances **32 shifts**. The seed is `0x1D2C3B4A`; zero is rejected; XOR mixing that produces zero retains the old state. Normal new-Match PREPARE mixes the game tick count as it stood **before the accepted Start edge**, whereas fixed-seed mode reloads the seed. Other Rounds continue the generator. [Model `lfsr.py:15–43`, `params.py:79–96`, `game_top.py:143,154,197–202`, `arena_ctrl.py:82–96`.]

XAPP052 Table 3 lists taps **32,22,2,1** for a maximum-length XNOR construction; copying its tap list does not specify this project's bit order, XOR variant or draw schedule. [XAPP052 **v1.1**, 1996-07-07, Table 3 p. 5](https://docs.amd.com/v/u/en-US/xapp052), accessed 2026-10-28. Prove the actual recurrence/reciprocal convention algebraically or with an independent reference, and record known-answer words. No maximal-period test was executed in this research.

**Options:** retain the current recurrence and draw-on-demand cadence (least scenario churn); use one shift per candidate (cheaper, different correlations and golden sequence); or use a parallel 32-shift transform (same sequence if proved, different area/timing). A different algorithm needs a reason beyond appearing more random. Start timing influence is required, cryptographic unpredictability is not. Capturing a fast counter gives finer variation but adds coherent capture and trace data; the existing game counter is easier to reproduce but groups Starts at tick resolution.

**Recommendation:** provisionally retain the bit-exact algorithm and slow-domain seed capture; specify every state advance, candidate address extraction, rejection limit, slot order, fixed-mode entry and zero recovery. This is contingent on the service scheduling decision. If search becomes preemptible, reproducibility must include the service arbitration schedule or define a deterministic candidate/installation ordering independent of variable stalls. Log seed, algorithm revision, draw index and installed candidates for diagnosis. Tests: first known-answer words, zero-mix case, reset/new-Match/next-Round behavior, repeat across stalls, and identical placement traces between model and HDL. The team selects algorithm/schedule; equivalence is measurable.

**Legal score bound is settled arithmetic:** before the final Step, a continuing Match has each player's total below the maximum goal 40. One surviving Bike can collect at most one +3 Reward plus +3 Survival Bonus: **39 + 3 + 3 = 45**. Six unsigned bits suffice for retained Points; two bits suffice for 0–3 Lives. Do not clamp to goal or 99. Explicitly size intermediate HDL additions and preserve both final totals before comparing victory; a crashed Bike cannot collect. [Specification — Match, Points Goal and scoring / Rewards; `params.py:71–76`; `score_unit.py:15–62`; `tests/test_model.py:133–138,559–625`.]

## 7. Input ordering, eligibility and UART reuse

**Current evidence:** `InputBatch` keeps the last vertical and horizontal request per Player per published tick, plus one Start flag; tied board samples pick UP over DOWN and RIGHT over LEFT. `TurnUnit` chooses the crossing axis against Heading at **application**, then updates Heading at launch. Inputs arrive two model ticks before application. Eligibility at arrival comes from the last render snapshot; game phase is checked again at application. [Model `input_batch.py:1–36,59–134`, `turn_unit.py:40–62`, `game_top.py:121–153,183–197`.]

Axis compression preserves “last valid request” **if the entire batch is evaluated against one fixed Heading**. It does not by itself prove equivalence to eligibility/validity at physical arrival across a launch. Example to settle: while Heading RIGHT, UP then LEFT arrives before a launch but is applied after that launch has changed Heading to UP. UP was valid and LEFT invalid at arrival; against the new Heading the compressed horizontal LEFT is valid. Is the whole batch deliberately owned by a later logical input tick, or must requests be split at the launch boundary? This is a timing-contract decision, not evidence that the specification has chosen either interpretation.

Likewise, phase-at-consumption alone lets a Start queued during Crash start a later Ready state. The retained analysis demonstrates that counterexample. Fast eligibility using a **display** snapshot can introduce a different error if coherent rendering intentionally lags control: a fresh Start after Ready entry may be rejected while the displayed snapshot still says Crash. Use an acknowledged control-eligibility epoch independently of display publication, and define the uncertain transition interval. [Experiment findings — Analysis against the existing Python model](CS-256%20UART%20Input%20Prototype%20Findings.md#analysis-against-the-existing-python-model); current arrival gating `game_top.py:123–125`.

**Options:** (A) ordered event records tagged with eligibility/round/reset epoch and an assigned logical input window; (B) fixed-window axis batches with a proved cutoff/Heading contract; (C) fast-domain prefilter against acknowledged authoritative Heading/phase plus version metadata. A is easiest to reason about but needs bounded buffering/consumption; B is compact but needs equivalence proof; C introduces replicated state and ack lag. **Provisional recommendation:** define logical window and eligibility boundaries first, then prove B against A as an uncompressed reference. Keep small bounded batches only if that equivalence holds across launch, Pause, Crash→Ready and new-Match transitions. Include cross-source Start ordering/deduplication, switch-goal capture and P1 debounce latency in the interface. An arbitrary first-batch discard must not discard a fresh post-entry event.

### Retained UART result and its limits

The experiment is substantial reusable transport evidence: all four Icarus and four XSim cases passed, a board LED wrapper routed at Vivado **2025.2 build 6299465**, with WNS **+7.344 ns**, WHS **+0.119 ns**, no critical CDC findings, but **five documented unwaived structural warnings**. The manifest pins the experiment source; current `analyze.py` was later adapted and differs from that historical hash. No physical board/browser test or game eligibility integration is established. [Evidence README](../../prototipos/fpga/I2-uart-input-prototype/README.md), [timing summary](../../prototipos/fpga/I2-uart-input-prototype/timing-summary.rpt), [CDC report](../../prototipos/fpga/I2-uart-input-prototype/cdc.rpt), [source manifest](../../prototipos/fpga/I2-uart-input-prototype/source-sha256.txt), [findings](CS-256%20UART%20Input%20Prototype%20Findings.md).

AMD's CDC report classifies clock pairs, exceptions and structural endpoint safety; reviewed warnings and protocol evidence are still needed beyond a summary count. [UG906 **2025.2**, Summary by Clock Pair](https://docs.amd.com/r/2025.2-English/ug906-vivado-design-analysis/Summary-by-Clock-Pair), accessed 2026-10-28. The experiment's Gray-pointer constraints and LED wrapper results do not establish X1 timing or game CDC safety.

The 64-entry queue is not unrestricted loss-free transport: 115200 8N1 permits **11520 bytes/s**, far above one event per 60 Hz consumer edge. Empty-to-full is about **5.6 ms** under sustained offered load; 64 reads take about **1.067 s**, excluding initial transfer delay. Dropped-newest overflow is explicit in the experiment. Options are browser ACK/credits, a proved application rate/burst bound with overflow telemetry, or a faster ordered fast-domain fold into bounded logical batches. UART transport should continue draining/qualifying during Pause, rejecting ineligible events so they cannot replay after resume. [Findings — Analysis against the existing Python model; `uart_async_fifo.sv` and `uart_input_path.sv` under the experiment.]

**Enter recommendation:** choose `0x0D` for browser Enter, `0x20` for Space, `0x0A` ignored; this already matches `input_batch.py:45–57` and the experimental decoder tests. Alternative CR/LF acceptance requires deduplication of CRLF and repeated Start prevention. This is an encoding choice requiring contract/browser consistency, not a physical UART unknown. The board's FTDI USB-UART bridge provides serial RX/TX; it does not define browser key encoding. [Digilent Nexys A7 manual, revised **2019-07-10**, §6](https://digilent.com/reference/_media/reference/programmable-logic/nexys-a7/nexys-a7_rm.pdf), accessed 2026-10-28.

Acceptance: independent ordered-stream reference for long bursts, UP→LEFT with initial RIGHT, invalid requests preserving an earlier valid Pending Turn, tied board events, events immediately before/after launch and every phase transition, Start held/repeated through PREPARE, Pause with queued input, reset with FIFO nonempty, overflow recovery without a phantom Start, and fresh Start after Ready. A finite FIFO cannot meet an unbounded “no loss” claim; state the permitted traffic envelope or flow-control contract.
