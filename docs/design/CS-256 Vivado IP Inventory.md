# CS-256 Vivado IP Inventory

Which Vivado IP each build uses, where its settings live, and where it is instantiated. Checked on 4 November 2026 against the commits named below; the `game_top` section was updated on 5 November 2026 for the one-Wizard change of [ADR 0006](../adr/0006-single-wizard-counter-game-clock-and-handout-as-guidance.md). Roman's rsws08 project could not be inspected, so anything about it is marked.

**`game_top` uses two IP cores: the Clocking Wizard (`clk_wiz` 6.0) and, with PR #35 and its build change on branch `build/sprite-rom`, `bike_rom` (Block Memory Generator 8.4).** Every other build uses only the Clocking Wizard. On 15 November 2026 Roman generated `bike_rom` for the Bike sprites; `drawcon` instantiates it, and `build_game_top.tcl` creates it from the catalog (see [`bike_rom`](#bike_rom-block-memory-generator)). On 16 November he generated `reward_rom` for the Rewards; nothing instantiates it yet (see [`reward_rom`](#reward_rom-block-memory-generator)). The memories in `core_blocks` are inferred from SystemVerilog (see [Memories](#memories-no-ip)).

## Rule: use the IP Vivado generates

Every Clocking Wizard in a synthesized build must be generated by Vivado from its IP Catalog. Do not replace one with a hand-written module, even one with the same name and ports.

- **`clk_wiz_0` is a module name, not a catalog item.** In the catalog, choose **Clocking Wizard** (`xilinx.com:ip:clk_wiz`) and set the Component Name, or use `create_ip` as `proyecto_final/build_game_top.tcl` does.
- **Settings must have a known source.** When the owner's `.xci` is unavailable, a regenerated Wizard is still real IP, but its settings are inferred. Say so, record them, and confirm them with the owner.
- **Stand-ins are for simulation only.** `proyecto_final/sim_clocks/` holds an ideal clock with the pixel Wizard's name, so a bench can run quickly; `proyecto_final/sim_models/bike_rom.sv` does the same for `bike_rom`. They never go into synthesis, and a bench that uses them does not test the IP.
- **A direct `MMCME2_BASE` is not a substitute.** The one in `prototypes/vga_106mhz/` is an experiment. Using a primitive in the game needs an ADR. It also has no Wizard to define the board clock, so it adds `prototypes/vga_106mhz/game_top_trial.xdc`.
- **The build makes three checks, and stops if one fails.** No design file may define a module named `clk_wiz_*`; a `clk_wiz` IP object from the catalog must exist for each Wizard name; and each instance must have the `inst/mmcm_adv_inst` structure with one `MMCME2_ADV`. **They do not confirm that the instance is the generated IP.** In a review, a renamed and edited copy of the Wizard's generated code passed all three and the build published its bitstream, so reviewing the sources still matters.

## `game_top` (the milestone build)

`proyecto_final/src/game_top.sv` is the top in PR 11 (`v4/moving-block`, `e5407d8`) and in `v4/moving-block-fixes`, which is now on `main`. Since the Paso 4c change ([ADR 0006](../adr/0006-single-wizard-counter-game-clock-and-handout-as-guidance.md)) it has one Wizard; `clk_juego` comes from a 20-bit counter on `clk_pix`. The tested bitstream in `proyecto_final/bitstreams/` predates this and still has both Wizards.

| Instance | Purpose | Instantiated at | Settings in the repository |
|---|---|---|---|
| `clk_wiz_0`, `u_clk` | `clk_pix`, from the 100 MHz board clock | `game_top.sv` | Created by `proyecto_final/build_game_top.tcl`, which stops unless M, D and O equal 28.375, 4 and 8.5, values copied from `proyecto_final/ip/clk_wiz_0/clk_wiz_0.xci`. It does not read the file |
| `bike_rom`, `bike_rom_1` and `bike_rom_2` | One Bike sprite ROM per Bike, read on `clk_pix` | `drawcon.sv` | Created by `build_game_top.tcl` with the settings of `proyecto_final/ip/bike_rom/bike_rom.tcl`, copied into the script, and the data of `proyecto_final/sprites/bike_synth.coe`. See [`bike_rom`](#bike_rom-block-memory-generator) |

Settings as built with Vivado 2025.2 on 4 November:

| Setting | `clk_wiz_0` |
|---|---|
| Input frequency | 100.000 MHz |
| Input source | `Single_ended_clock_capable_pin` |
| Requested output | 83.46 MHz |
| **Achieved output** | **83,455,882 Hz** |
| M / D / O | 28.375 / 4 / 8.500 |
| Reset and locked ports | Off |

A 20-bit counter on `clk_pix` toggles `clk_juego` every 695,466 cycles: 83,455,882.35 Hz / (2 × 695,466) = 59.99997 Hz. `game_top_timing.xdc` defines it with `-divide_by 1390932`.

Before Paso 4c, `game_top` also had `clk_wiz_1` (instance `u_clk1`), chained from `clk_pix` with `No_buffer` and requesting 5 MHz: M / D / O 44.125 / 6 / 122.750, achieved 4,999,995 Hz, and the divider toggled every 41,667 of its cycles (59.9995 Hz). Those settings were inferred, because Roman's `clk_wiz_1.xci` is only on rsws08. `game_top_fixes.bit`, now kept only in Git history (see the [bitstream guide](../../proyecto_final/bitstreams/README.md)), is that two-Wizard build; `bitstreams/game_top_one_wizard.bit` is the one-Wizard build tested on the board on 12 November.

### Open problems

- **`clk_wiz_0.xci` is not portable as committed.** It records Vivado 2020.2 (`RUNTIME_PARAM.SWVERSION`), was customized for another part (`PROJECT_PARAM.DEVICE` is `xc7vx485t`), and writes outputs to `../../../../DigitalDesignsFinalProject.gen/`. Vivado 2025.2 reports it as locked and upgrades it from revision 6 to 17. Its frequency settings survive the upgrade. Adding it with `add_files` from another location failed in one build, because the output path falls outside the run folder; `import_ip` works. `main` keeps this file for Roman's project, but its build does not read it, which avoids the upgrade's critical warning.
- **The Vivado version on rsws08 is not confirmed.** The `.xci` suggests 2020.2. A `.xci` written by 2025.2 may not open there, which is why `main` creates its Wizard from Tcl. That script has only been run on 2025.2.

## `bike_rom` (Block Memory Generator)

The Bike sprite ROM for `game_top`, as the course's sprite tips build it. Generated by Roman in Vivado 2020.2 on myws on 15 November 2026, for `xc7a100tcsg324-1`. `drawcon` instantiates two, one per Bike, on branch `hdl/sprites` (PR #35).

| Setting | Value |
|---|---|
| Memory type | Single Port ROM, Native interface |
| Size | 1024 × 12 bits (RGB444), address width 10 |
| Read latency | 2 cycles of the read clock: primitive output register on, core output register off |
| Ports | `clka`, `ena` (enable pin; tie to 1), `addra[9:0]`, `douta[11:0]`; no reset |
| Contents | `proyecto_final/sprites/bike_synth.coe`, made by `tools/png2coe.py` from `assets/candidates/bike-synth-32.png` |
| Resources | One 18K BRAM (Vivado's Summary tab) |

- `proyecto_final/ip/bike_rom/bike_rom.xci` is the generated file, kept as the record. It records Vivado 2020.2 and paths relative to Roman's myws project: the `.coe` as `../../../../../FPGA/proyecto_final/sprites/bike_synth.coe` and the outputs under `DigitalDesignsFinalProject.gen/`, so it only resolves in that layout.
- `proyecto_final/ip/bike_rom/bike_rom.tcl` creates the same IP with `create_ip` in any open project, finding the `.coe` from its own location. It has not been run yet.
- Only the settings go in the repository. The output products Vivado makes from them (wrappers, simulation models, the synthesized checkpoint) are regenerated and are not committed.
- **Build.** `proyecto_final/build_game_top.tcl` (mode `full`) creates `bike_rom` with `create_ip` in its output folder, with the settings of `bike_rom.tcl` copied into the script and `generate_synth_checkpoint false`, as for `clk_wiz_0`. It stops unless the IP is `xilinx.com:ip:blk_mem_gen`, a Single Port ROM of 1024 × 12 with the primitive output register on, the core output register off and the `.coe` loaded. Since PR #48 no constraint names the BRAMs: the `set_max_delay` that once ended at them was removed with X1. Its first check also stops if a design file defines `module bike_rom`.
- **Simulation.** `proyecto_final/sim_models/bike_rom.sv` is a stand-in with the same ports and 2 cycles of latency. As in the IP, which has no `regcea` pin, `ena` gates both stages. Before the benches start, the build converts `bike_synth.coe` to `tests/bike_synth.mem`; the stand-in and `game_top_tb` read it with `$readmemh` (`-testplusarg bike_mem=<file>`), so the data lives only in the `.coe`.
- **As built** with Vivado 2025.2 on 16 November 2026: `blk_mem_gen` 8.4, core revision 12, one `RAMB18E1` per ROM (`prim_init.ram/…SIMPLE_PRIM18.ram`, so the cell's `PRIMITIVE_GROUP` is `BMEM`, which the timing filter does not use). The generated simulation model (`C_HAS_MEM_OUTPUT_REGS_A = 1`) and the stand-in agreed on every cycle of a one-off check: all 1024 words, then 20,000 random addresses with random `ena`, and a word appears 2 rising edges after its address. `CONFIG.READ_LATENCY_A` reads 1 and does not count the output register.
- **Timing.** `drawcon` computes each ROM address on `clk_pix` from `pos_link`'s `draw*` registers, which are on `clk_pix` too (X1, PR #48), so the ROM inputs are ordinary `clk_pix` paths. The positions and headings cross earlier, into `pos_link`'s `pend*` registers; see [`proyecto_final/README.md`](../../proyecto_final/README.md#clocks-and-crossings).

## `reward_rom` (Block Memory Generator)

The Reward sprite ROM: both Reward images in one memory. A pixel can fall inside at most one Reward, because each Reward fills exactly one Cell and no two share a Cell, so one read per cycle is enough. Generated by Roman in Vivado 2020.2 on myws on 16 November 2026, for `xc7a100tcsg324-1`, with the same settings as `bike_rom` except the depth. Not instantiated yet: it waits for the Arena, which gives the Reward Cells.

| Setting | Value |
|---|---|
| Memory type | Single Port ROM, Native interface |
| Size | 512 × 12 bits (RGB444), address width 9 |
| Address | `{sel, a_y, a_x}`: `sel` 0 is the +1 gem (words 0–255), 1 the +3 star (256–511); `a_x`, `a_y` are `curr_x[3:0]`, `curr_y[3:0]`, since Rewards are aligned to the 16 px Cells |
| Read latency | 2 cycles of the read clock: primitive output register on, core output register off |
| Ports | `clka`, `ena` (enable pin; tie to 1), `addra[8:0]`, `douta[11:0]`; no reset |
| Contents | `proyecto_final/sprites/reward_neon.coe`, made by `tools/png2coe.py` from `assets/candidates/reward-neon-gem-16.png` and `reward-neon-star-16.png`, stacked in that order |

- `proyecto_final/ip/reward_rom/reward_rom.xci` is the generated file, kept as the record, with the same myws-relative paths as `bike_rom.xci`.
- `proyecto_final/ip/reward_rom/reward_rom.tcl` creates the same IP with `create_ip` in any open project. It has not been run yet.

## Vendor primitives (not IP)

These are instantiated directly and need no IP generation.

| Primitive | Where | Purpose |
|---|---|---|
| `IBUF` | `tron_top.sv`, `block_top.sv`, `core_board_top.sv`, `uart_input_board.sv` | One input buffer for the board clock, shared by two Wizards |

## Rules

- Record **achieved** frequencies, not requested ones.
- Prefer creating a Wizard from Tcl with its settings written down. A committed `.xci` is tied to the Vivado version and project that made it.
- When a build adds, removes or changes an IP, update this note in the same change.
- To check a build, read its `<name>-frequency.txt` and `<name>-properties.txt`, or run this in Vivado after opening the project: `report_property [get_ips <name>]`.
