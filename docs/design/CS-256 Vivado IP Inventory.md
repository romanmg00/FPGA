# CS-256 Vivado IP Inventory

Which Vivado IP each build uses, where its settings live, and where it is instantiated. Checked on 4 November 2026 against the commits named below; the `game_top` section was updated on 5 November 2026 for the one-Wizard change of [ADR 0006](../adr/0006-single-wizard-counter-game-clock-and-handout-as-guidance.md). Roman's rsws08 project could not be inspected, so anything about it is marked.

**The only IP core any build uses is the Clocking Wizard (`clk_wiz` 6.0).** No build uses Block Memory Generator: the memories are inferred from SystemVerilog (see [Memories](#memories-no-ip)).

## Rule: use the IP Vivado generates

Every Clocking Wizard in a synthesized build must be generated by Vivado from its IP Catalog. Do not replace one with a hand-written module, even one with the same name and ports.

- **`clk_wiz_0` is a module name, not a catalog item.** In the catalog, choose **Clocking Wizard** (`xilinx.com:ip:clk_wiz`) and set the Component Name, or use `create_ip` as `proyecto_final/build_game_top.tcl` does.
- **Settings must have a known source.** When the owner's `.xci` is unavailable, a regenerated Wizard is still real IP, but its settings are inferred. Say so, record them, and confirm them with the owner.
- **Stand-ins are for simulation only.** `proyecto_final/sim_clocks/` holds an ideal clock with the pixel Wizard's name, so a bench can run quickly. It never goes into synthesis, and a bench that uses it does not test the Wizard.
- **A direct `MMCME2_BASE` is not a substitute.** The one in `prototypes/vga_106mhz/` is an experiment. Using a primitive in the game needs an ADR. It also has no Wizard to define the board clock, so it adds `prototypes/vga_106mhz/game_top_trial.xdc`.
- **The build makes three checks, and stops if one fails.** No design file may define a module named `clk_wiz_*`; a `clk_wiz` IP object from the catalog must exist for each Wizard name; and each instance must have the `inst/mmcm_adv_inst` structure with one `MMCME2_ADV`. **They do not confirm that the instance is the generated IP.** In a review, a renamed and edited copy of the Wizard's generated code passed all three and the build published its bitstream, so reviewing the sources still matters.

## `game_top` (the milestone build)

`proyecto_final/game_top.sv` is the top in PR 11 (`v4/moving-block`, `e5407d8`) and in `v4/moving-block-fixes`, which is now on `main`. Since the Paso 4c change ([ADR 0006](../adr/0006-single-wizard-counter-game-clock-and-handout-as-guidance.md)) it has one Wizard; `clk_juego` comes from a 20-bit counter on `clk_pix`. The tested bitstream in `proyecto_final/bitstreams/` predates this and still has both Wizards.

| Instance | Purpose | Instantiated at | Settings in the repository |
|---|---|---|---|
| `clk_wiz_0`, `u_clk` | `clk_pix`, from the 100 MHz board clock | `game_top.sv` | Created by `proyecto_final/build_game_top.tcl`, which stops unless M, D and O equal 28.375, 4 and 8.5, values copied from `proyecto_final/ip/clk_wiz_0/clk_wiz_0.xci`. It does not read the file |

Settings as built with Vivado 2025.2 on 4 November:

| Setting | `clk_wiz_0` |
|---|---|
| Input frequency | 100.000 MHz |
| Input source | `Single_ended_clock_capable_pin` |
| Requested output | 83.46 MHz |
| **Achieved output** | **83,455,882 Hz** |
| M / D / O | 28.375 / 4 / 8.500 |
| Reset and locked ports | Off |

A 20-bit counter on `clk_pix` toggles `clk_juego` every 695,466 cycles: 83,455,882.35 Hz / (2 × 695,466) = 59.99997 Hz. `game_top_timing.xdc` defines it with `-divide_by 1390932`.

Before Paso 4c, `game_top` also had `clk_wiz_1` (instance `u_clk1`), chained from `clk_pix` with `No_buffer` and requesting 5 MHz: M / D / O 44.125 / 6 / 122.750, achieved 4,999,995 Hz, and the divider toggled every 41,667 of its cycles (59.9995 Hz). Those settings were inferred, because Roman's `clk_wiz_1.xci` is only on rsws08. `game_top_fixes.bit`, now kept only in Git history (see the [bitstream guide](../../proyecto_final/bitstreams/README.md)), is that two-Wizard build; `bitstreams/game_top_one_wizard.bit` is the one-Wizard build tested on the board on 12 November.

### Open problems

- **`clk_wiz_0.xci` is not portable as committed.** It records Vivado 2020.2 (`RUNTIME_PARAM.SWVERSION`), was customized for another part (`PROJECT_PARAM.DEVICE` is `xc7vx485t`), and writes outputs to `../../../../DigitalDesignsFinalProject.gen/`. Vivado 2025.2 reports it as locked and upgrades it from revision 6 to 17. Its frequency settings survive the upgrade. Adding it with `add_files` from another location failed in one build, because the output path falls outside the run folder; `import_ip` works. `main` keeps this file for Roman's project, but its build does not read it, which avoids the upgrade's critical warning.
- **The Vivado version on rsws08 is not confirmed.** The `.xci` suggests 2020.2. A `.xci` written by 2025.2 may not open there, which is why `main` creates its Wizard from Tcl. That script has only been run on 2025.2.

## Other builds

Each of these creates its Wizards from Tcl in its own build folder, so none has a committed `.xci`. All use a 100 MHz input with `No_buffer`, one shared `IBUF`, and reset and locked off, except the clock probe, which tests other inputs.

| Build | Branch | Module names | Requested | Created by |
|---|---|---|---|---|
| Moving block | `t3/basic-systemverilog-blocks`, committed | `video_pixel_clock`, `video_game_clock` | 83.46 MHz, 4.6875 MHz | `prototypes/moving_block/run.tcl` |
| Moving block | Same branch, staged and uncommitted | `clk_wiz_0`, `clk_wiz_1` | 83.46 MHz, 4.6875 MHz | Same file |
| Full Tron game | `t3/basic-systemverilog-blocks` | `tron_pixel_clock`, `tron_base_clock` | 83.46 MHz, 4.6875 MHz | `prototypes/core_blocks/game/run_tron.tcl` |
| Core board and video experiments | `t3/basic-systemverilog-blocks` | `video_pixel_clock`, `video_game_clock` | 83.46 MHz, 4.6875 MHz | `core_blocks/board/run_board.tcl`, `core_blocks/video/clock_feasibility.tcl` |
| Clock probe | `t3/basic-systemverilog-blocks` | `probe_shared`, `probe_cascade` and others | Feasibility only | `core_blocks/crossing/clock_probe.tcl` |
| UART experiment | `main` and later | `uart_pixel_clock`, `uart_game_clock` | 83.46 MHz, 5.000 MHz | `prototypes/uart_input/run.tcl` |

Since Paso 4c, `build_game_top.tcl` generates one Wizard and checks that `-divide_by` in `game_top_timing.xdc` equals 2 × `CLK_JUEGO_N` from `game_top.sv`, and the only `.xci` `main` tracks is `clk_wiz_0.xci`, which that build does not read.

The UART experiment also generates `axi_uartlite` and `axi_uart16550` from the catalog, only to inspect their interfaces. No design instantiates them.

## Rules

- Record **achieved** frequencies, not requested ones.
- Prefer creating a Wizard from Tcl with its settings written down. A committed `.xci` is tied to the Vivado version and project that made it.
- When a build adds, removes or changes an IP, update this note in the same change.
- To check a build, read its `<name>-frequency.txt` and `<name>-properties.txt`, or run this in Vivado after opening the project: `report_property [get_ips <name>]`.
